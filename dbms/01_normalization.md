# Normalization for Relay

## Introduction

Relay is a small payment API. It stores registered users, API keys generated by those users, payment transactions, and webhook updates sent by payment gateways.

## Unnormalized Form (UNF)

In the unnormalized form, all attributes are kept in one wide table. Repeating groups exist because a single user can have multiple API keys, multiple payments, and multiple webhook events.

| user_id | name | email | password_hash | api_keys (id, name, key_hash) | payments (id, amount, currency, provider, status) | webhook_events (id, event_type, payload) |
|---|---|---|---|---|---|---|
| 1 | Ishaan | ishaan@example.com | pass_hash_1 | (1, Dev Key, k_hash_1), (2, Prod Key, k_hash_2) | (101, 500.00, INR, stripe, success), (102, 1200.00, INR, razorpay, pending) | (1, payment.succeeded, {"id": 101}), (2, payment.pending, {"id": 102}) |
| 2 | Rahul | rahul@example.com | pass_hash_2 | (3, Default Key, k_hash_3) | (103, 750.00, INR, stripe, success) | (3, payment.succeeded, {"id": 103}) |
| 3 | Priya | priya@example.com | pass_hash_3 | (4, Test Key, k_hash_4) | (104, 2500.00, INR, paypal, failed) | (4, payment.failed, {"id": 104}) |

## First Normal Form (1NF)

To reach 1NF, we remove repeating groups so that every cell holds a single atomic value. We flatten the data into individual rows.

Composite primary key: (user_id, key_id, payment_id, event_id)

| user_id | name | email | password_hash | key_id | key_name | key_hash | payment_id | amount | currency | provider | status | event_id | event_type |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | Ishaan | ishaan@example.com | pass_hash_1 | 1 | Dev Key | k_hash_1 | 101 | 500.00 | INR | stripe | success | 1 | payment.succeeded |
| 1 | Ishaan | ishaan@example.com | pass_hash_1 | 2 | Prod Key | k_hash_2 | 102 | 1200.00 | INR | razorpay | pending | 2 | payment.pending |
| 2 | Rahul | rahul@example.com | pass_hash_2 | 3 | Default Key | k_hash_3 | 103 | 750.00 | INR | stripe | success | 3 | payment.succeeded |
| 3 | Priya | priya@example.com | pass_hash_3 | 4 | Test Key | k_hash_4 | 104 | 2500.00 | INR | paypal | failed | 4 | payment.failed |

This table satisfies 1NF because all attributes are atomic. However, it has lots of duplicate data. User details repeat across multiple rows, which causes insertion, update, and deletion issues.

## Second Normal Form (2NF)

A table is in 2NF if it is in 1NF and contains no partial dependencies. All non-key attributes must depend on the whole primary key, not just a part of it.

In the 1NF table, we have partial dependencies:
- user_id -> name, email, password_hash
- key_id -> user_id, key_name, key_hash
- payment_id -> user_id, amount, currency, provider, status
- event_id -> payment_id, event_type

To remove partial dependencies, we split the single table into separate tables based on what depends on what:

### Table: users
Primary key: id

| id | name | email | password_hash | created_at |
|---|---|---|---|---|
| 1 | Ishaan | ishaan@example.com | pass_hash_1 | 2026-01-10 10:00:00 |
| 2 | Rahul | rahul@example.com | pass_hash_2 | 2026-01-11 11:30:00 |

### Table: api_keys
Primary key: id
Foreign key: user_id references users(id)

| id | user_id | key_hash | name | created_at |
|---|---|---|---|---|
| 1 | 1 | k_hash_1 | Dev Key | 2026-01-10 10:05:00 |
| 2 | 1 | k_hash_2 | Prod Key | 2026-01-12 14:00:00 |

### Table: payments
Primary key: id
Foreign key: user_id references users(id)

| id | user_id | amount | currency | provider | status | created_at |
|---|---|---|---|---|---|---|
| 101 | 1 | 500.00 | INR | stripe | success | 2026-01-15 09:20:00 |
| 102 | 1 | 1200.00 | INR | razorpay | pending | 2026-01-16 12:10:00 |

### Table: webhook_events
Primary key: id
Foreign key: payment_id references payments(id)

| id | payment_id | event_type | payload | received_at |
|---|---|---|---|---|
| 1 | 101 | payment.succeeded | {"id": 101} | 2026-01-15 09:21:00 |
| 2 | 102 | payment.pending | {"id": 102} | 2026-01-16 12:10:30 |

## Third Normal Form (3NF)

A table is in 3NF if it is in 2NF and has no transitive dependencies. Non-key attributes must not depend on other non-key attributes.

Functional dependencies for each table:

1. users
- id -> name, email, password_hash, created_at
- email -> id, name, password_hash, created_at
Both id and email are candidate keys. There are no transitive dependencies.

2. api_keys
- id -> user_id, key_hash, name, created_at
- key_hash -> id, user_id, name, created_at
Both id and key_hash are candidate keys. All non-key attributes depend directly on candidate keys.

3. payments
- id -> user_id, amount, currency, provider, status, created_at
The primary key is id. No non-key attribute determines any other non-key attribute.

4. webhook_events
- id -> payment_id, event_type, payload, received_at
The primary key is id. All attributes depend directly on id without transitive dependencies.

The final four tables in 3NF:
- users(id, name, email, password_hash, created_at)
- api_keys(id, user_id, key_hash, name, created_at)
- payments(id, user_id, amount, currency, provider, status, created_at)
- webhook_events(id, payment_id, event_type, payload, received_at)

Relationships:
- One user has many api_keys
- One user has many payments
- One payment has many webhook_events

## Boyce-Codd Normal Form (BCNF)

A table is in BCNF if for every functional dependency X -> Y, X is a superkey. In all four tables, every determinant is a superkey. In users, id and email are superkeys. In api_keys, id and key_hash are superkeys. In payments and webhook_events, the id column is the only determinant and acts as the primary key. Since there are no non-trivial dependencies where the determinant is not a superkey, all four tables are in BCNF.
