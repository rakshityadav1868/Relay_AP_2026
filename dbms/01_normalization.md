# Normalization for Relay

## Introduction

Relay is a small payment API. It stores users, API keys generated by users, payments, and webhook events received for those payments.

## Unnormalized Form (UNF)

In the unnormalized table, all attributes are stored together in one wide table with repeating groups.

| user_id | name | email | password_hash | api_keys (id, name, key_hash) | payments (id, amount, currency, provider, status) | webhook_events (id, event_type, payload) |
|---|---|---|---|---|---|---|
| 1 | Ishaan | ishaan@example.com | pass_hash_1 | (1, Dev Key, k_hash_1), (2, Prod Key, k_hash_2) | (101, 500.00, INR, stripe, success), (102, 1200.00, INR, razorpay, pending) | (1, payment.succeeded, {"id": 101}), (2, payment.pending, {"id": 102}) |
| 2 | Rahul | rahul@example.com | pass_hash_2 | (3, Default Key, k_hash_3) | (103, 750.00, INR, stripe, success) | (3, payment.succeeded, {"id": 103}) |
| 3 | Priya | priya@example.com | pass_hash_3 | (4, Test Key, k_hash_4) | (104, 2500.00, INR, paypal, failed) | (4, payment.failed, {"id": 104}) |

## First Normal Form (1NF)

We remove repeating groups so each cell has a single value.

Primary key: (user_id, key_id, payment_id, event_id)

| user_id | name | email | password_hash | key_id | key_name | key_hash | payment_id | amount | currency | provider | status | event_id | event_type |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | Ishaan | ishaan@example.com | pass_hash_1 | 1 | Dev Key | k_hash_1 | 101 | 500.00 | INR | stripe | success | 1 | payment.succeeded |
| 1 | Ishaan | ishaan@example.com | pass_hash_1 | 2 | Prod Key | k_hash_2 | 102 | 1200.00 | INR | razorpay | pending | 2 | payment.pending |
| 2 | Rahul | rahul@example.com | pass_hash_2 | 3 | Default Key | k_hash_3 | 103 | 750.00 | INR | stripe | success | 3 | payment.succeeded |
| 3 | Priya | priya@example.com | pass_hash_3 | 4 | Test Key | k_hash_4 | 104 | 2500.00 | INR | paypal | failed | 4 | payment.failed |

Every field is atomic, so this is in 1NF. But user and payment data repeat in multiple rows.

## Second Normal Form (2NF)

We remove partial dependencies so non-key columns depend on the full primary key.

Partial dependencies in 1NF:
- user_id -> name, email, password_hash
- key_id -> user_id, key_name, key_hash
- payment_id -> user_id, amount, currency, provider, status
- event_id -> payment_id, event_type

We split into four tables:

### users
Primary key: id

| id | name | email | password_hash | created_at |
|---|---|---|---|---|
| 1 | Ishaan | ishaan@example.com | pass_hash_1 | 2026-01-10 10:00:00 |
| 2 | Rahul | rahul@example.com | pass_hash_2 | 2026-01-11 11:30:00 |

### api_keys
Primary key: id, Foreign key: user_id -> users(id)

| id | user_id | key_hash | name | created_at |
|---|---|---|---|---|
| 1 | 1 | k_hash_1 | Dev Key | 2026-01-10 10:05:00 |
| 2 | 1 | k_hash_2 | Prod Key | 2026-01-12 14:00:00 |

### payments
Primary key: id, Foreign key: user_id -> users(id)

| id | user_id | amount | currency | provider | status | created_at |
|---|---|---|---|---|---|---|
| 101 | 1 | 500.00 | INR | stripe | success | 2026-01-15 09:20:00 |
| 102 | 1 | 1200.00 | INR | razorpay | pending | 2026-01-16 12:10:00 |

### webhook_events
Primary key: id, Foreign key: payment_id -> payments(id)

| id | payment_id | event_type | payload | received_at |
|---|---|---|---|---|
| 1 | 101 | payment.succeeded | {"id": 101} | 2026-01-15 09:21:00 |
| 2 | 102 | payment.pending | {"id": 102} | 2026-01-16 12:10:30 |

## Third Normal Form (3NF)

We check for transitive dependencies. All non-key columns must depend only on candidate keys.

Functional dependencies:
- users: id -> name, email, password_hash, created_at (also email -> id, name, password_hash, created_at)
- api_keys: id -> user_id, key_hash, name, created_at (also key_hash -> id, user_id, name, created_at)
- payments: id -> user_id, amount, currency, provider, status, created_at
- webhook_events: id -> payment_id, event_type, payload, received_at

There are no transitive dependencies in any of the tables.

Final four tables:
- users(id, name, email, password_hash, created_at)
- api_keys(id, user_id, key_hash, name, created_at)
- payments(id, user_id, amount, currency, provider, status, created_at)
- webhook_events(id, payment_id, event_type, payload, received_at)

Relationships:
- one user has many api_keys
- one user has many payments
- one payment has many webhook_events

## Boyce-Codd Normal Form (BCNF)

A table is in BCNF if for every functional dependency X -> Y, X is a superkey. In all four tables, every determinant is a candidate key or superkey. There are no non-trivial dependencies where the left side is not a superkey. So all four tables are in BCNF.
